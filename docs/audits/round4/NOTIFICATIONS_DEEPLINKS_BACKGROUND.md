## Release blockers (every Fail)

Ordered by severity. The first six are, in my assessment, genuinely release-blocking; the remainder
are Fails that a named authority could formally accept for a demo-build release.

1. **NDB-8.02 — iOS push is dead.** No `.entitlements`, no `aps-environment`. Round 3's finding,
   unfixed. All FCM code is unreachable on the primary platform.
2. **NDB-1.01 — notification IDs overflow 32 bits for ~80% of medications.** Proven empirically
   against the app's own test fixtures. `zonedSchedule` throws; the reminder is never created; the
   awaited loop in `rescheduleAll` aborts every remaining medication.
3. **NDB-6.01 — Android declares none of the three receivers the plugin requires.** Scheduled
   notifications never display, never survive reboot, actions never process.
4. **NDB-3.01 — drug name and dose render on the lock screen.** `'Insulin Glargine 20 units'`, no
   redaction, no `NotificationVisibility.private`. The app's own `SessionScope` comment names this
   threat and the fix was applied only to the patient-switch case.
5. **NDB-5.01 — the "Taken ✓" action tells the patient their dose was recorded when nothing is
   recorded.** A false clinical statement on an adherence path.
6. **NDB-7.01 — timezone is resolved by a first-match offset guess** because `tz.local` is always
   UTC and `flutter_timezone` is absent; daily repeats have no course-end expiry.
7. NDB-3.05 — FCM token never deleted or unregistered on logout/patient switch.
8. NDB-4.03 — cold-start tap routing is unreachable code (`consumePendingNotification` races an
   un-awaited future).
9. NDB-2.01 / 2.02 / 2.03 / 2.04 — permission requested twice with no rationale; nine preference
   toggles with zero consumers that never reach the sender.
10. NDB-1.02 / 1.03 — no environment separation; `SCHEDULE_EXACT_ALARM` declared but unused (Play
    restricted-permission risk).
11. NDB-4.01 / 4.02 — no account binding on any routed notification; no deep-link configuration at
    all (consistent with open BUG-23).
12. NDB-5.05 — every notification string is hard-coded English, violating the CLAUDE.md i18n contract.
13. NDB-6.02 / 6.05, NDB-7.02 / 7.03, NDB-8.01 / 8.03 / 8.04 — no intent persistence, no honest
    delivery state, no scheduling authority, no quiet hours, no monitoring, no smoke test, no kill
    switch.

## Limitations of this audit

- **MASTER-4.04: this is a source review, not a release-artifact review.** No `flutter build`,
  `flutter test`, `flutter clean`, or `pod install` was run, per the brief. No device or simulator
  was used, so no notification was actually delivered, tapped, or observed on a lock screen.
- **One exception, disclosed:** I ran a standalone `dart run` of a 25-line scratch file in the session
  scratchpad (`idcheck.dart`) that reimplements `_generateNotificationId` and evaluates it against the
  app's own test fixtures. It touched no project file and produced no build artefact. Its output is
  the evidence for NDB-1.01 and is reproducible from the formula at `medication_reminder_service.dart:287-289`
  plus the bound at `flutter_local_notifications_platform_interface-12.0.0/lib/src/helpers.dart:6`.
- Package behaviour claims (timezone default-UTC, `validateId` bound, required Android receivers,
  `UILocalNotificationDateInterpretation` scope) are cited to the **pinned package sources in
  `~/.pub-cache`**, not to documentation, and each carries a file:line reference.
- Two backend repos were read for payload shapes; neither yielded a patient-facing send site, so
  NDB-3.01's server-side half and NDB-7.02's authority question remain partly unverified — recorded
  as BLOCKED-OWNER rather than assumed.
- Firebase console, App Store Connect, and Apple Developer portal state is out of reach; the three
  BLOCKED-OWNER items above are the complete list of what that costs.
- I did not audit the destination screens' own authorization (the last line of defence for NDB-4.01)
  — that belongs to the security/privacy module.
